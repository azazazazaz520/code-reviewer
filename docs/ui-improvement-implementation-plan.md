# UI 改进实施方案

- 初版日期：2026-07-21
- 当前复核日期：2026-08-12
- 当前状态：已完成响应式基础改造，下一轮进入核心工作流与可访问性交互改进

## 1. 背景

当前前端已经形成稳定的视觉与组件基础，包括 Tailwind CSS、shadcn/ui 风格组件、主题 token、深色模式、Skeleton 加载态，以及围绕代码审查场景建立的风险等级色彩。现阶段不需要整体更换视觉风格，主要工作是补齐页面身份、长任务反馈、错误恢复、移动端操作和可访问交互，使 Dashboard、仓库详情和审查详情能够稳定承载高频代码审查工作。

本方案以当前代码和 2026-08-12 UI 复核结果为基线。2026-07-21 的原始实施内容保留在文末“历史实施记录”中，不再作为当前待办重复执行。

## 2. 目标

1. 让用户在审查任务的等待、运行、成功、失败和报告不可用状态下，都能立即确认当前审查对象、状态和下一步操作。
2. 让风险、Finding、审查进度和恢复入口更容易扫描、定位和执行。
3. 将移动导航、自定义弹窗、密集行操作和状态播报收敛到可访问、可复用的交互模式。
4. 建立统一的前端错误展示边界，避免在主区域直接暴露 Axios、代理或模型服务原始错误。
5. 保持现有设计 token、深色模式和控制台信息密度，不引入割裂的新视觉体系。

## 3. 非目标与边界

1. 不进行与 UI 目标无关的业务数据结构重构。
2. 不引入新的大型 UI 框架；优先复用现有 Base UI、shadcn/ui 风格组件和主题 token。
3. 不把工具型控制台改造成营销型首页或以装饰效果为主的页面。
4. 不一次性替换所有原生表单控件；只处理核心工作流中存在一致性、反馈或可访问性问题的控件。
5. 允许为页面上下文补充最小、向后兼容的 API 响应字段，例如为审查状态补充仓库显示信息；不得借此扩展无关后端能力。
6. 提示词工作台的具体交互优化由 `docs/devprompt-pro-implementation-plan.md` 负责；本方案只管理跨业务复用的 Button、Tabs、Dialog、错误反馈和设计 token 规范。

## 4. 当前基线

### 4.1 已完成能力

1. 全局 Layout 已增加移动端顶部栏和覆盖层导航，桌面端保留可折叠侧边栏。
2. 导航激活态已支持详情页前缀匹配。
3. 页面主容器已使用响应式宽度和间距。
4. Dashboard、RepoList、RepoDetail 和 ReviewDetail 的主要栅格已改为响应式布局。
5. 通用 Table 组件已经提供横向滚动容器，核心表格在窄屏下不会直接挤压所有列。
6. FindingCard、ReviewHeatmap 和 ReviewProgress 的主要点击区域已改为语义化按钮，并补充了部分焦点样式和 ARIA 状态。
7. ReviewDetail 已具备风险摘要、Finding 严重级别筛选、诊断信息、Reviewer 原始输出和 Diff 展示。

`docs/system-design.md` 中的前端技术栈仍记录为 React 18 和 Ant Design 5，且路由表未包含提示词工作台，与当前 React 19、Tailwind CSS、Base UI 和 shadcn/ui 风格实现不一致。进入本方案实施前，应先修正该文档的技术栈和路由现状，避免架构依据与实际实现互相冲突。

## 5. 2026-08-12 当前审查结论

本轮基于当前前端代码、桌面宽屏页面、375px 视口页面以及当次前端构建和 lint 结果进行复核。在已检查范围内没有发现新增的发布阻断级 P0 UI 问题。由于后端当时未运行，仪表盘、真实审查报告、完整 Finding 和表格数据尚未完成端到端验收，因此该结论不能扩展到未验证状态。

当前优先级集中在以下方面：

1. 审查任务在所有状态下的页面身份和上下文。
2. 移动导航、弹窗和键盘焦点管理。
3. 长任务状态播报、日志跟随和用户阅读控制。
4. 统一错误说明、诊断信息和恢复入口。
5. 移动端主要操作及危险操作的点击目标。

## 6. P1：下一轮必须完成

### P1-1 建立审查详情的统一页面身份

#### 现状

`frontend/src/pages/ReviewDetail.tsx` 的成功状态从“返回”按钮和风险 Badge 开始，没有明确的页面主标题。运行状态只渲染 ReviewProgress；失败、报告不可用和状态不可用页面使用局部标题，均缺少稳定的审查对象上下文。

前端 ReviewTask 类型声明了可选 `repo_name`，但当前 `GET /api/reviews/{task_id}` 直接返回 ReviewTask 数据库对象，没有填充该字段。按照“仓库名称 · PR / Commit”的目标实施时，必须先闭合数据来源。

#### 实施要求

1. 抽取所有状态共享的 ReviewHeader 或等价页面头部。
2. 页面使用唯一且明确的 `h1`，标题固定表达“审查报告”或“代码审查”。
3. 在标题附近展示仓库名称、来源类型、PR 或 Commit、分支和任务状态；没有值时使用明确占位，不显示误导性信息。
4. 等待、准备、运行、成功、失败和报告不可用状态复用同一页面身份区域。
5. 风险等级继续作为视觉重点，但不承担页面主标题职责。
6. 优先由后端状态接口以向后兼容方式填充 `repo_name`；如果采用前端额外请求，必须定义加载失败、仓库已删除和历史名称变化时的展示行为。

#### 验收标准

1. 每一种任务状态都存在且仅存在一个明确的页面主标题。
2. 用户进入页面后无需滚动即可看到仓库、审查来源、目标 Revision 或 PR，以及当前状态。
3. 仅状态接口成功、仅报告接口成功或部分请求失败时，页面仍保留已获取的上下文。
4. 仓库名称的数据来源通过 API Schema、前端类型和接口实现共同确认，不依赖始终为空的可选字段。

### P1-2 收敛移动导航和弹窗交互

#### 现状

移动导航已经支持打开、关闭和当前项高亮，但覆盖层没有完整的 dialog 语义和焦点管理。打开后焦点仍停留在触发按钮，背景页面仍可参与键盘和辅助技术导航。SubmitReviewModal 和仓库编辑 overlay 也需要收敛到同一套可访问弹层模式。

#### 实施要求

1. 优先复用同一套 Dialog、Drawer 或等价 primitive，不分别手写焦点 trap、背景隔离和焦点恢复。
2. 弹层具有可读标题，并建立 `role="dialog"`、`aria-modal="true"` 和标题关联。
3. 打开后将焦点移入弹层；关闭后恢复到触发按钮。
4. Tab 和 Shift+Tab 不得离开模态弹层，Escape 可以关闭。
5. 弹层打开期间，背景内容不得继续参与键盘交互和辅助技术阅读。
6. 遮罩只承担指针关闭操作，不与可见关闭按钮形成重复、同名的辅助技术入口。
7. 导航切换路由、Escape、遮罩和关闭按钮四种关闭路径使用相同的清理和焦点恢复逻辑。

#### 验收标准

1. 仅使用键盘可以打开导航、遍历导航项、切换页面和关闭导航。
2. 打开弹层后，焦点不会进入背景页面；关闭后回到原触发按钮。
3. SubmitReviewModal 和仓库编辑弹窗满足相同的标题、焦点、Escape 和恢复规则。
4. 375px、768px 和 1440px 视口下，导航及弹窗不遮挡必须操作的内容。

### P1-3 改造审查进度播报与日志跟随

#### 现状

`frontend/src/components/ReviewProgress.tsx` 在日志变化时调用 `scrollIntoView({ behavior: "smooth" })`。该调用可能连带滚动外层页面，也会在用户阅读旧日志时持续把视图拉回底部。运行状态和日志区域目前没有稳定的状态播报语义。

#### 实施要求

1. 对“等待执行”“审查进行中”“审查完成”“审查失败”等状态使用独立的 `role="status"` 和 `aria-live="polite"`。
2. live region 只播报当前状态或最新一条重要事件，不把整个日志列表设为 live region。
3. 使用日志容器自身的 `scrollTop` 或 `scrollTo` 控制内部滚动，不再依赖底部元素的 `scrollIntoView`。
4. 仅当用户位于日志底部附近时自动跟随；用户向上滚动后暂停跟随。
5. 暂停跟随后显示“有新日志”或“回到底部”入口，用户主动恢复后再继续跟随。
6. 保留日志区域最大高度和内部滚动，长日志不得撑开整个报告页。
7. 在 `prefers-reduced-motion: reduce` 下使用即时滚动，并关闭非必要旋转、脉冲和滑动效果。

#### 验收标准

1. 新日志不会改变报告页外层滚动位置。
2. 用户离开日志底部后，新日志不会抢夺阅读位置。
3. 状态变化可以被屏幕阅读器获知，但普通日志不会造成连续重复播报。
4. 运行结束、失败和重新加载后，自动跟随状态能够正确重置。

### P1-4 建立统一的前端错误边界

#### 现状

Dashboard、RepoList、RepoDetail、SubmitReviewModal 和 PromptWorkbench 分别维护局部 `getErrorMessage`，后端没有返回 detail 时会直接回退到 Axios message。`frontend/src/lib/error-message.ts` 主要处理模型服务错误字符串，尚未覆盖 HTTP、网络和业务错误的统一映射。

#### 实施要求

1. 建立统一的传输层错误转换函数，输入 unknown error 和业务场景，输出用户说明、诊断信息、是否可重试和建议恢复动作。
2. 主区域优先显示后端返回的用户可理解业务说明。
3. 对 401、402、429、502、503、超时、无响应和未知错误提供稳定映射。
4. Axios message、原始状态码和代理错误只保留在可折叠诊断区域或日志中。
5. Dashboard、RepoList、RepoDetail、ReviewDetail、SubmitReviewModal 和 PromptWorkbench 复用同一错误转换边界。
6. 阻断性错误提供明确的重试或配置入口；局部数据失败不得无条件覆盖页面其他已成功内容。

建议的主说明：

| 场景 | 主说明 |
| --- | --- |
| 502 / 503 | 审查服务暂时不可用，请确认服务已启动后重试 |
| 网络断开或无响应 | 无法连接到审查服务，请检查服务状态或网络 |
| 请求超时 | 请求处理时间较长，请稍后重试 |
| 401 | 服务认证失败，请检查相关配置后重试 |
| 402 | 模型服务余额不足，请补充余额或更换服务后重试 |
| 429 | 请求过于频繁，请稍后重试 |
| 后端业务错误 | 显示后端返回的用户可理解说明 |

#### 验收标准

1. 主区域不再显示“Request failed with status code 502”等技术错误。
2. 相同错误在不同页面使用一致的主说明和恢复入口。
3. 技术诊断仍可被开发和支持人员获取。
4. 错误映射具有独立单元测试，不依赖页面手工触发。

### P1-5 调整移动端点击目标和危险操作布局

#### 现状

共享 Button 默认高度为 32px，sm 为 28px，部分表格行操作还使用 `h-auto p-0`。在移动端密集操作中，查看、编辑、归档和删除入口容易误触。

44×44 CSS px 是本项目对移动端主要操作和高风险操作采用的易用性目标。WCAG 2.2 AA 的最低目标是 24×24 CSS px，或满足对应的目标间距例外；不得把 44×44px 表述为所有控件的最低合规线。

#### 实施要求

1. 移动端主要操作、图标按钮和高风险操作优先达到 44×44 CSS px。
2. 其他密集操作至少满足 24×24 CSS px 或相应间距要求。
3. 不全局放大所有 Button，保留桌面控制台的合理信息密度。
4. 表格中的多个行操作优先收敛到“更多”菜单，或使用具有明确最小点击区域的按钮。
5. 删除、归档和恢复等危险操作与普通导航操作保持足够间距，并继续使用文字和图标双重表达。
6. 视觉尺寸需要保持紧凑时，可以扩大实际点击容器，但不得形成与相邻操作重叠的目标。

#### 验收标准

1. 375px 视口下，主要操作和危险操作能够稳定点击，不依赖精细指向。
2. 相邻小目标满足尺寸或间距要求。
3. 桌面表格未因全局 Button 放大而显著降低信息密度。
4. 删除、归档和查看操作在移动端不会紧密排列为无内边距文字链接。

## 7. P2：P1 完成后推进

### P2-1 动画降级

1. 在 `frontend/src/index.css` 中增加统一的 `prefers-reduced-motion` 规则。
2. 将 `transition-all` 收敛为明确的 opacity、transform 或尺寸属性。
3. 在减少动画模式下关闭或缩短旋转、脉冲和平滑滚动。
4. 保留状态变化本身，不通过关闭动画隐藏加载或完成状态。

### P2-2 路由级拆包与性能预算

当前构建记录显示主 JavaScript chunk 约 755kB，gzip 约 228kB。`frontend/src/App.tsx` 静态引入所有页面，ReviewDetail 还包含 Recharts 和较多报告渲染逻辑。

实施要求：

1. 对 RepoDetail、ReviewDetail 和 PromptWorkbench 使用路由级动态加载。
2. 为异步路由提供稳定、可访问的 Suspense 加载状态。
3. 将 Recharts 延迟到实际进入报告页时加载。
4. Reviewer 原始输出、长日志和 Diff 只在展开后挂载重内容。
5. 每次实施记录初始路由、异步路由和总构建体积的前后对比。
6. 构建后不应继续出现未经说明的单个主入口 chunk 超过 500kB 警告；如果保留例外，必须记录组成和后续拆分边界。

### P2-3 Dashboard 与 ReviewDetail 信息层级

1. Dashboard 明确当前总体风险、待处理高危 Finding 和最近审查状态。
2. 风险分布和热力图显示时间范围、仓库范围、总量、空状态和错误状态。
3. ReviewDetail 保持“页面身份—风险摘要—阻断问题—Finding—诊断信息—原始输出”的层级。
4. Finding 继续按严重级别筛选，并保证文件、行号、影响和建议优先于诊断元数据。
5. 不增加装饰性渐变、发光和复杂动效；专业感主要来自信息可扫描性、状态准确性和操作反馈。

### P2-4 主题与组件一致性

1. 明确 primary、severity、muted、border、ring 的职责，避免主操作和风险等级争夺颜色语义。
2. 检查浅色和深色模式下的文本、按钮、风险 Badge、图表和弹窗对比度。
3. 统一 Card 密度、标题字号、间距和边框，避免无必要的卡片嵌套。
4. 危险操作继续使用 destructive variant，并结合图标和文字，不只依赖颜色。

### P2-5 提示词工作台转交边界

以下问题已确认，但具体方案和验收应写入 `docs/devprompt-pro-implementation-plan.md`：

1. PromptOutputPanel 空结果区固定使用 `min-h-[28rem]`，空状态过度占据首屏。
2. 结果 Tabs 缺少 tabpanel、`aria-controls`、`aria-labelledby`、roving tabindex 和方向键切换。

本方案只保留可复用于代码审查页面的 Tabs、Button、错误映射和动画降级规范。

## 8. 建议实施批次

### 批次 A：审查页面身份与数据契约

范围：

- ReviewDetail 所有状态的统一 ReviewHeader。
- 仓库名称和审查对象的数据来源。
- API Schema、前端类型和历史数据兼容。

完成条件：等待、运行、成功、失败和报告不可用状态均能显示一致的页面身份。

### 批次 B：弹层与长任务可访问交互

范围：

- 移动导航的 Dialog 或 Drawer 语义。
- SubmitReviewModal 和仓库编辑弹窗的统一 primitive。
- ReviewProgress 状态播报、内部滚动和暂停跟随。

完成条件：核心流程能够仅使用键盘完成，弹层焦点和日志阅读位置稳定。

### 批次 C：错误恢复与移动端操作

范围：

- 统一错误转换边界。
- Dashboard、仓库页面、审查详情和提交弹窗接入。
- 移动端行操作和危险操作布局。

完成条件：错误说明一致、可恢复，移动端主要操作不依赖精细点击。

### 批次 D：性能与视觉一致性

范围：

- 路由级动态加载和构建体积记录。
- 动画降级。
- Dashboard、ReviewDetail 信息层级和主题对比度。

完成条件：前端构建、lint 和新增测试通过，构建体积变化有明确记录。

每个批次保持单一责任边界。布局、数据契约、可访问交互、错误治理和性能拆包不合并为一个难以审查的大改动。

## 9. 验证方案

### 9.1 自动验证

当前 `frontend/package.json` 没有 test 脚本，也没有前端组件测试基础设施。“运行现有测试”不是可执行的验收项。P1 实施应增加最小前端测试能力，例如 Vitest、React Testing Library 和 jsdom，并至少覆盖：

1. 统一错误映射的状态码、网络错误、业务错误和 fallback。
2. 移动导航打开、Escape 关闭和焦点恢复。
3. ReviewProgress 在用户离开底部后暂停跟随，并在主动恢复后继续跟随。
4. ReviewDetail 各任务状态的主标题和上下文。
5. 提示词 Tabs 的测试由 DevPrompt Pro 方案负责。

所有批次执行：

- `npm.cmd run build`
- `npm.cmd run lint`
- 新增的前端测试命令

### 9.2 人工验证矩阵

| 范围 | 验证场景 | 通过条件 |
| --- | --- | --- |
| 响应式 | 375px、768px、1440px | 无非预期页面级横向滚动；表格可在自身容器内滚动 |
| 键盘 | Tab、Shift+Tab、Enter、Space、Escape | 可以完成导航、提交、筛选、展开、关闭和恢复焦点 |
| 审查状态 | 等待、准备、运行、成功、失败、报告不可用 | 每个状态都有页面身份、状态说明和下一步操作 |
| 日志 | 自动跟随、用户上滚、新日志、回到底部 | 新日志不抢夺用户阅读位置，不滚动外层页面 |
| 错误 | 401、402、429、502、503、超时、无响应、业务错误 | 主说明可理解，技术详情可获取，恢复入口明确 |
| 数据 | 空 Finding、正常 Finding、降级报告、部分请求失败 | 已成功内容保留，阻断信息与诊断信息分层 |
| 主题 | 浅色、深色、减少动画 | 文本和状态可读，减少动画模式不出现非必要运动 |
| 移动操作 | 行操作、图标按钮、危险操作 | 目标尺寸或间距满足项目要求，无明显误触风险 |

### 9.3 端到端验证

后端可用后，至少创建以下真实审查任务：

1. 正常完成且有 Finding。
2. 正常完成且无 Finding。
3. Reviewer 部分失败但生成降级报告。
4. 审查任务失败。
5. 报告读取失败或服务中途不可用。

端到端验证需要同时检查 API 响应、审查日志、报告页面和 Electron sidecar 输出。验证结束后关闭本次启动的后端、Vite 和 Electron 进程，并确认相关端口已经释放。
