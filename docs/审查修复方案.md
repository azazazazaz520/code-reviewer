# 审查报告问题修复方案

## 1. 这份方案要解决什么问题

审查报告中列出了 8 个问题。它们可能造成三类后果：

- 审查器读取了本次审查范围之外的文件；
- 代码没有被完整审查，但报告看起来像已经审查完成；
- 报告中出现了无法验证、定位错误或与变更无关的问题。

修复完成后，每次审查都应满足以下要求：

1. 只能读取本次审查固定版本中的文件。
2. 能够说明哪些文件和代码片段已经被审查。
3. 每条 Finding（审查问题）都有真实的文件、行号、证据、影响和修复建议。
4. 每种变更都有明确的审查方式；没有覆盖的内容必须明确显示。
5. 混合提交中的不同文件只发送给相关的 Reviewer。
6. 一次审查从开始到结束使用同一份模型配置。

## 2. 8 个问题和修复重点

| 编号 | 问题 | 修复重点 | 优先级 |
| --- | --- | --- | --- |
| 1 | ReadFile 可以读取快照外的文件 | 给文件读取工具绑定快照根目录 | P1 |
| 2 | Diff 和文件内容可能被静默截断 | 分批审查，并记录覆盖范围 | P1 |
| 3 | FindingGate 对行号、证据和影响检查不足 | 增加真实位置和可信证据校验 | P1 |
| 4 | Planning 可能没有安排任何审查 | 为每类文件设置默认审查责任 | P1 |
| 5 | 路径处理会破坏隐藏配置目录和 .env | 统一路径规范化规则 | P2 |
| 6 | 中文文件名在提交/合并请求审查中可能失效 | 使用 NUL 分隔的版本控制路径输出 | P2 |
| 7 | 混合提交会把无关文件发送给 Reviewer | 按文件和 Diff 片段分配上下文 | P2 |
| 8 | Reviewer 可能继续使用旧模型配置 | 按审查任务创建并固定 LLM 客户端 | P2 |

## 3. 调整后的审查流程

参考成熟的静态分析分层方式，审查流程应先建立固定版本的代码数据库，再执行查询，最后由 LLM 解释查询结果。建议流程调整为：

~~~text
创建审查任务
    ↓
固定代码快照和模型配置
    ↓
在快照上建立代码数据库
    ↓
执行与变更类别对应的查询和确定性检查
    ↓
根据查询结果选择关联代码片段
    ↓
将查询结果和受控代码片段交给 Reviewer
    ↓
FindingGate 校验 Finding
    ↓
检查覆盖范围、错误和截断情况
    ↓
生成最终报告
~~~

代码分析的核心流程可以概括为：

~~~text
固定版本源码
    ↓
代码提取器
    ↓
代码数据库
    ↓
查询规则
    ↓
带有文件和行号的分析结果
~~~

当前项目不必一开始就覆盖所有语言和分析能力。建议先复用现有的 CRG，并补充文件、符号、引用和调用关系索引，形成项目自己的代码数据库。后续可以为受支持的编程语言和持续集成配置增加查询适配器。

### 3.1 本项目的分层对应关系

| 分析层次 | 本项目对应设计 |
| --- | --- |
| 固定版本的源码 | ReviewSnapshot 和 revision |
| 代码提取器 | 从快照提取文件、符号、引用、调用关系和配置结构的代码 |
| 代码数据库 | ReviewCodeDatabase，首期可以由 CRG 和语言解析结果组成 |
| 查询规则 | 安全、配置、Workflow、依赖和影响范围查询 |
| 查询结果 | 带有文件、行号、规则编号和证据的 AnalysisResult |
| 标准化分析结果 | 转换为项目内部的 Check、Finding 和 EvidenceRecord |
| 源码归档 | 与数据库绑定的快照源码，不能指向用户当前工作目录 |

查询可以遍历整个代码数据库来理解跨文件关系，但结果必须定位到当前变更或明确的关联位置。LLM 不负责决定可以读取哪些路径，也不直接从文件系统中搜索任意文件。

### 3.2 代码数据库的最小设计

第一版不需要覆盖全部静态分析能力，但应保留清晰的核心分层：

| 数据 | 最少需要记录的内容 |
| --- | --- |
| 数据库信息 | database_id、revision、构建时间、构建工具版本、状态 |
| 文件 | 相对路径、语言、文件哈希、是否成功解析 |
| 符号 | 函数、类、方法、接口、定义位置 |
| 引用 | 符号被引用的位置 |
| 调用关系 | 调用方、被调用方和调用位置 |
| 数据流（按语言能力提供） | 输入、传播节点、危险操作和对应位置 |
| 查询结果 | result_id、rule_id、文件、行号、消息和证据引用 |

第一版至少实现文件、符号、引用和调用关系。数据流能力可以按语言逐步增加；依赖数据流的查询在当前语言不支持时，应记录 unverified 或 limitation，不能假定查询已经完成。

代码数据库应在快照创建后构建一次，并以 revision 作为唯一版本标识。后续 Query、Reviewer 和 FindingGate 都使用同一个数据库。

代码提取可能出现三种状态：

- complete：计划文件全部成功解析；
- partial：部分文件无法解析，但已明确列出；
- failed：数据库无法用于本次审查。

partial 或 failed 状态必须进入报告。partial 状态下可以继续审查能够解析的内容，但报告不能标记为完整。

这样处理后，Reviewer 仍然可以理解跨文件逻辑：查询可以找到相关定义、调用方和数据流；文件读取只服务于已经批准的查询结果。代码数据库无法提供某项关系时，报告会显示限制，Reviewer 不能用猜测补足证据。

本文中的几个术语含义如下：

- **快照**：本次审查使用的固定代码版本；
- **Reviewer**：调用 LLM 分析代码的审查器；
- **Tool**：Reviewer 可以调用的工具，例如 ReadFile；
- **代码数据库**：从固定快照提取出的文件、符号、引用、调用关系和规则分析结果；
- **查询结果**：由代码数据库查询产生的、带有真实文件和行号的分析结果；
- **Finding**：报告中的单个审查问题；
- **确定性校验器**：通过解析器、规则或 Schema 检查内容，不依赖 LLM 猜测；
- **覆盖范围**：已经读取并审查的文件、Diff 片段和代码行。

## 4. 修复一：限制 Tool 只能访问审查快照

### 4.1 建立任务级 Tool 上下文

每次审查创建一个只读的 Tool 上下文，至少包含：

~~~text
repo_root：本次审查快照的根目录
revision：快照对应的提交 SHA
database_id：与快照绑定的代码数据库编号
approved_context_refs：由 Review Plan 和查询结果产生的允许上下文引用
~~~

repo_root 必须来自 ReviewSnapshot.repo_root。它不能来自模型输出，也不能默认使用当前进程的工作目录。

Tool Registry 可以继续保存工具名称、Schema 和实现，但真正执行工具时必须传入当前任务的上下文。全局 Registry 不保存某个任务的目录，避免多个审查任务互相影响。

直接变更文件由 Review Plan 自动批准；关联文件只能由查询结果批准。Reviewer 需要更多信息时，应请求符号、调用关系或数据流查询；引擎执行查询后，将查询结果中的文件和行号加入 approved_context_refs。

ReadFile 只作为受控的代码片段读取接口使用。它不能成为 Reviewer 任意搜索文件系统的入口。优先由引擎根据查询结果读取指定行范围，并把读取记录绑定到查询结果。

### 4.2 修改 ReadFile

ReadFile 只接受由引擎批准的相对路径和行号范围，并按以下顺序处理：

1. 拒绝绝对路径、盘符路径、UNC 路径和空字节。
2. 统一 Windows 和 Unix 路径分隔符。
3. 将路径与快照根目录拼接后执行实际路径解析。
4. 确认解析后的路径仍在快照根目录内。
5. 解析符号链接后再次检查路径范围。
6. 拒绝访问版本控制元数据目录。
7. 确认文件和行号范围来自当前任务的 approved_context_refs；直接变更文件还必须符合 Review Plan。
8. 文件不存在或路径越界时返回明确的 Tool 错误。

当前 collect_context_node 也会直接拼接路径后调用 read_file。这条路径必须使用同一个安全读取函数，不能绕过 Tool 的路径检查。

### 4.3 测试要求

新增测试覆盖：

- snapshot/../outside.txt 被拒绝；
- 快照外的绝对路径被拒绝；
- 指向快照外部的符号链接被拒绝；
- 持续集成配置文件、.env 等合法隐藏路径可以读取；
- 未出现在查询结果或批准上下文中的同仓库文件不能被 Reviewer 直接读取；
- 查询结果引用的文件和行号可以被正确读取；
- 两个并发审查任务的快照根目录不会串用。

## 5. 修复二：让审查覆盖范围可见

### 5.1 取消无法追踪的静默截断

当前 Reviewer 会直接截取：

- Diff 的前 4,000 个字符；
- 每个文件内容的前 2,000 个字符；
- ReadFile 返回的前 200 行。

这些截断会导致后面的代码没有进入审查上下文。应由统一的上下文构建模块负责分批，并记录每个批次的范围。

代码数据库承担“查找关联代码”的工作。Reviewer 不需要为了理解调用关系而自行翻阅大量文件。查询先返回符号定义、调用方、被调用方、数据流和相关测试，再由引擎从结果中选择少量代码片段。

每个上下文批次至少记录：

~~~json
{
  "file": "src/app.py",
  "start_line": 1,
  "end_line": 200,
  "char_count": 4632,
  "truncated": false,
  "source": "changed_file"
}
~~~

如果单个批次达到字符上限，应创建下一个批次。确实发生截断时，输入和报告中都要显示，例如：

~~~text
[内容已截断：当前显示第 1～200 行，剩余内容将在后续批次处理]
~~~

### 5.2 按文件和 Diff 片段分批

Diff 应按文件和 Hunk（连续变更片段）拆分。文件内容应按行范围拆分。

审查状态中增加以下信息：

~~~json
{
  "database_status": "ready",
  "extraction_status": "complete",
  "extracted_files": 48,
  "planned_files": 25,
  "covered_files": 20,
  "planned_hunks": 31,
  "covered_hunks": 24,
  "query_results": 12,
  "uncovered_files": ["src/file_21.py"],
  "uncovered_hunks": 7,
  "truncated_inputs": 0,
  "coverage_status": "incomplete"
}
~~~

### 5.3 修改 Reflection 的停止条件

Reflection 不应根据“有没有 Finding”判断审查是否完成。没有发现问题，可能表示代码没有问题，也可能表示代码还没有被读取。

Reflection 应检查：

- 代码数据库是否成功建立；
- 代码提取是否覆盖了计划审查的文件；
- 是否还有未处理的 Diff Hunk；
- 查询是否覆盖了变更涉及的函数、符号和数据流；
- 是否还有未读取的、已经被查询结果批准的关联上下文；
- 是否发生 Tool 错误或模型输出截断；
- 是否仍有 Reflection 轮次预算。

建议规则：

1. 代码数据库创建失败时，不生成“审查完整”的报告。
2. 有未覆盖 Diff Hunk 或未完成的必要查询且还有预算时，继续处理下一批。
3. 所有计划内容和必要查询都已完成时，允许结束。
4. 达到最大轮次但仍有未覆盖内容时，结束流程并将状态标记为 degraded。
5. 空 Finding、行号为 0 或 FindingGate 拒绝某条 Finding，都不能单独说明审查已经完成。

### 5.4 修改报告状态

review_status=complete 需要同时满足：

- 没有 Workflow Error；
- 代码数据库创建成功；
- 代码提取没有影响本次审查的错误；
- 没有未处理的模型输出截断；
- coverage_status=complete；
- 所有计划中的 Reviewer 和校验器都有结果。

否则使用 degraded，并显示失败步骤或未覆盖范围。

risk_level=low 只说明当前已接受的 Finding 中没有更高严重级别。它不能代替覆盖状态，也不能证明所有代码都已经审查。

## 6. 修复三：加强 FindingGate

### 6.1 证据来源由引擎决定

模型返回的字段不能直接证明 Finding 来自可信检查。建议先产生 AnalysisResult，再允许 LLM 对结果进行解释。

AnalysisResult 至少包含：

~~~json
{
  "result_id": "query-001",
  "database_id": "db-001",
  "revision": "abc123",
  "rule_id": "security.command-injection",
  "file": "src/runner.py",
  "line_start": 42,
  "line_end": 45,
  "message": "用户输入进入 shell 命令",
  "evidence_refs": ["source-001", "dataflow-001"]
}
~~~

这个结果由引擎和查询产生，模型只能补充原因、影响和建议，不能自行伪造查询结果。

建议规则：

- 查询和确定性校验器产生的结果统一由引擎标记为 evidence_type=static_check，并记录数据库编号、规则编号和 revision；
- Reviewer 只负责解释 AnalysisResult，生成的候选标记为 evidence_type=reviewer；
- Tool 证据记录真实的 Tool 调用编号、工具名称、参数和结果摘要；
- 模型不能通过自行输出 static_check 或 tool_call_id 提高 Finding 的可信等级；
- 无法验证的外部信息使用 unverified Check 展示，不生成 Finding。

Finding 可以关联如下证据：

~~~json
{
  "evidence_refs": [
    {
      "source": "diff",
      "file": "src/auth.py",
      "line_start": 42,
      "line_end": 45,
      "database_id": "db-001",
      "result_id": "query-001"
    }
  ]
}
~~~

### 6.2 校验文件和行号

每条候选 Finding 都要经过以下检查：

1. 文件路径经过统一规范化。
2. 文件确实属于本次变更或被明确声明为关联上下文。
3. 文件存在于审查快照中。
4. 正行号不超过文件实际行数。
5. Reviewer Finding 默认应定位到新增或修改行。
6. 如果允许定位到关联上下文行，必须标记为 reviewer_context，并说明它与本次变更的关系。
7. 行号为 0 只允许确定性校验器或明确的文件级检查使用。

例如，第 999,999 行应在 FindingGate 阶段被拒绝，不能进入风险等级计算。

### 6.3 校验原因、影响和建议

最低要求如下：

- reason 必须说明具体的失败、攻击或兼容性场景；
- suggestion 必须说明可以执行的修复动作；
- 纯命名偏好、格式差异和“建议检查”不能生成 Finding；
- 影响分类必须属于系统支持的范围；
- 文件定位、原因和影响需要相互对应。

FindingGate 应保留过滤原因，例如：

~~~text
line_out_of_range
untrusted_evidence
uncertain_claim
unrelated_file
duplicate_finding
~~~

这些原因用于报告诊断和质量统计。

## 7. 修复四：让 Planning 覆盖所有重要变更

### 7.1 设置文件类别的默认责任

安全关键词可以追加审查，但不能作为安全审查的唯一入口。建议使用以下默认责任：

| 文件类别 | 默认审查方式 |
| --- | --- |
| source_code | Security Query Pack + Style；脚本语言再加 Performance |
| configuration | Configuration Query Pack + Validator；必要时加 Security |
| ci_workflow | Workflow Query Pack + Validator + Security |
| release_manifest | Release Manifest Validator |
| dependency_lock | Dependency Query Pack + Validator |
| documentation | 默认不生成通用 Finding；记录明确策略 |
| generated_artifact | 默认不生成通用 Finding；记录已识别为生成产物 |
| unknown | 记录“暂不支持此类文件”的限制 |

每种文件类别都先执行对应的 Query Pack（查询规则集合）。Query Pack 可以检查整个代码数据库，但结果必须定位到当前变更或其直接影响范围。Reviewer 使用查询结果和少量代码片段生成说明，不能代替查询规则。

其中：

- 反向代理配置文件应进入配置校验；
- 持续集成配置文件应检查权限和命令执行风险；
- 包含 dangerouslySetInnerHTML 的 TSX 至少应进入 Security 基线或专门的前端安全检查；
- update/windows.json 继续使用发布清单校验器，不进入通用 Style Reviewer。

### 7.2 增加配置和 Workflow 查询及校验器

优先增加两个确定性查询及校验模块。它们都在固定快照的代码数据库上运行，并输出带有规则编号、文件和行号的 AnalysisResult。

#### Configuration Query Pack 和 Validator

至少检查：

- 反向代理服务的目录索引、监听地址和目录暴露；
- 明文密钥、Token 和密码；
- JSON、YAML、TOML 的解析错误；
- 项目已经声明的配置 Schema；
- 明显危险的配置开关。

#### Workflow Query Pack 和 Validator

至少检查：

- permissions: write-all 等过宽权限；
- pull_request_target 与不可信输入的组合；
- Shell 命令中的未约束变量；
- 第三方 Action 是否固定版本；
- 工作流是否把不可信内容直接用于命令。

校验器返回三类结果：

- pass：检查通过；
- fail：发现有确定性证据的问题；
- unverified：需要外部信息，当前无法确认。

### 7.3 空计划的报告规则

如果某类文件暂时没有适配的 Reviewer 或校验器，报告必须显示检查限制，例如：

~~~text
该文件类型当前没有可用的专用校验器，未执行通用审查。
~~~

这种情况下，报告不能仅显示 complete 和 low，让用户误以为检查已经充分完成。

## 8. 修复五：统一路径处理和版本控制文件名读取

### 8.1 新增共享路径模块

新增一个共享模块，例如：

~~~text
backend/app/engine/paths.py
~~~

由以下模块统一使用：

- scope.py；
- finding_gate.py；
- Diff 路径解析；
- Tool 文件读取；
- Snapshot 文件列表处理。

统一规则：

1. 统一使用 / 作为路径分隔符。
2. 只移除明确的 ./ 前缀。
3. a/ 和 b/ Diff 前缀单独处理。
4. 保留持续集成配置目录、.env 以及其他以点开头的文件和目录。
5. Tool 请求中的绝对路径和 .. 路径直接拒绝。
6. 所有模块使用相同的路径比较规则。

不能继续使用 lstrip("./") 处理路径，因为它会同时删除多个点和斜杠。

### 8.2 使用 NUL 分隔的版本控制路径

changed_files 改为使用版本控制命令按 NUL 分隔输出路径：

~~~text
<base> 与 <revision> 之间的变更路径，按 NUL 分隔输出
~~~

读取结果按 NUL 切分，不能按普通换行切分，也不能把版本控制工具的八进制转义结果当作真实文件名。

Diff Hunk 中的文件路径也要统一解码。测试至少覆盖：

- 中文文件名；
- 空格；
- 引号；
- 制表符；
- 重命名文件；
- 隐藏文件。

## 9. 修复六：按文件范围给 Reviewer 提供上下文

### 9.1 结构化 Review Plan

当前 review_plan 只有 Reviewer 名称，无法表达某个 Reviewer 负责哪些文件。

Review Plan 应同时包含两类任务：

- Query Assignment：执行哪些查询，查询可以跨文件分析；
- Reviewer Assignment：哪个 Reviewer 负责解释哪些查询结果。

Query Assignment 示例：

~~~json
{
  "query": "security.command-injection",
  "files": ["src/runner.py"],
  "traverse": ["callers", "callees", "dataflow"],
  "reason": "变更代码调用了命令执行接口"
}
~~~

Reviewer Assignment 示例：

~~~json
{
  "reviewer": "style_reviewer",
  "files": ["src/app.ts"],
  "query_results": ["query-002"],
  "diff_hunks": [
    {"file": "src/app.ts", "new_start": 20, "new_count": 6}
  ],
  "related_files": [],
  "reason": "源码变更"
}
~~~

review_plan 旧字段可以暂时保留，用于兼容历史代码；新执行逻辑使用结构化分配。

### 9.2 执行时过滤

执行顺序应调整为：

1. Query 在完整代码数据库上运行；
2. 引擎保存查询结果和真实代码位置；
3. 引擎根据查询结果选择必要的代码片段；
4. Reviewer 只解释分配给自己的查询结果和代码片段。

每个 Reviewer 只能收到：

- 分配给自己的变更文件；
- 这些文件对应的 Diff Hunk；
- 查询结果引用的关联文件；
- 与自身职责匹配的 Tool。

关联文件要单独标记为 related_context，并使用独立的文件数和字符预算。

Reviewer 如果需要更多上下文，应请求一个查询，例如“查找这个函数的调用方”，不能直接提交任意文件路径。引擎执行查询并校验结果后，再决定是否增加上下文。

对于同时修改 update/windows.json 和 src/app.ts 的提交：

- src/app.ts 进入 Style 和 Security Reviewer；
- update/windows.json 进入 Release Manifest Validator；
- 发布清单不进入 Style Reviewer 的直接上下文；
- 只有存在真实依赖关系时，发布清单才作为明确标记的关联上下文传入。

### 9.3 测试要求

使用可以记录输入的测试 Reviewer，验证：

- Style Reviewer 的 changed_files 不包含发布清单；
- Style Reviewer 的 Diff 不包含发布清单 Hunk；
- Release Manifest Validator 仍能读取完整发布清单；
- 关联文件会被标记，并计入关联上下文预算。

## 10. 修复七：按任务固定 LLM 配置

### 10.1 创建 SettingsSnapshot

Workflow 开始时读取一次模型配置，并保存本次审查使用的配置版本：

~~~json
{
  "model": "configured-model",
  "base_url": "configured-base-url",
  "temperature": 0.1,
  "max_tokens": 4096,
  "config_version": 3
}
~~~

API Key 只用于创建客户端，不写入 ReviewState、日志或报告。

### 10.2 使用 Reviewer 工厂

REVIEWER_REGISTRY 保存 Reviewer 类或工厂函数，不保存带有旧 LLM 状态的长期实例。

建议流程：

~~~text
审查任务
    ↓
读取 SettingsSnapshot
    ↓
创建任务级 LLMProvider
    ↓
按 Reviewer 名称创建 Reviewer
    ↓
执行本次审查
~~~

设置更新后的行为：

- 已开始的任务继续使用自己的 SettingsSnapshot；
- 新任务读取新配置；
- Reviewer 不因创建时间不同而使用不同版本的全局配置；
- 不依赖清空全局 LLM 来刷新长期 Reviewer。

如果短期内必须保留实例缓存，应在设置更新时清除所有 Reviewer 的缓存，并增加并发保护。这只能作为过渡方案，长期方案应使用工厂和依赖注入。

## 12. 回归测试清单

### 代码数据库

- 数据库只能由当前审查快照创建；
- 数据库记录的 revision 与 ReviewSnapshot 一致；
- 查询结果中的文件和行号能在快照源码中找到；
- 修改同一个文件后重新审查会创建新数据库，不复用旧版本结果；
- 单个文件解析失败时，数据库记录 partial 状态和失败文件；
- 数据库构建失败时，报告不能标记为 complete；
- 查询结果可以找到变更函数的定义、调用方和被调用方；
- 查询结果包含规则编号、result_id 和证据位置。

### Tool 和路径

- 快照外相对路径、绝对路径和外部符号链接全部被拒绝；
- 持续集成配置文件和 .env 分类正确；
- 未被查询结果或 Review Plan 批准的同仓库文件不能被 Reviewer 直接读取；
- Tool 不读取当前进程目录或源仓库目录；
- 并发任务之间的快照根目录互不影响。

### 覆盖和 Reflection

- 25 个文件在首批处理 20 个时会继续处理剩余 5 个；
- 代码数据库和代码提取状态会计入覆盖结果；
- 空 Finding、行号为 0 和被 Gate 拒绝的 Finding 不会让覆盖状态提前完成；
- 达到最大轮次后仍有未覆盖内容时，报告为 degraded；
- Diff、文件内容和输出截断都会记录范围。

### FindingGate

- 第 999,999 行和超过实际文件长度的 Finding 被拒绝；
- 变更文件中的上下文行必须具备真实文件和因果证据；
- 模型伪造 static_check、tool_call_id 或证据引用不能提高可信等级；
- 命名偏好、建议检查和外部未验证事实不会进入 Finding；
- 过滤原因能出现在质量指标或诊断信息中。

### Planning 和混合提交

- 反向代理配置文件进入配置校验器；
- CI Workflow 的过宽权限进入 Workflow Validator；
- TSX 的危险 HTML 注入模式进入安全检查；
- 发布清单由确定性校验器处理；
- 混合提交时各 Reviewer 只收到被分配的文件和 Diff。

### 版本控制和模型配置

- 中文、空格、引号、制表符和重命名文件名可以正确解析；
- 设置更新后新任务使用新配置；
- 已开始任务不会中途更换模型、服务地址或 API Key；
- 不同 Reviewer 不会因创建时间不同产生配置漂移。

## 13. 验收标准

完成修复后，应满足：

1. 所有文件读取都能追溯到当前审查任务的快照根目录。
2. 代码数据库的 revision 与审查快照一致，查询结果可以定位到真实源码。
3. 代码提取失败、查询失败或数据库不完整时，报告会显示具体限制。
4. 报告显示计划文件数、已覆盖文件数、未覆盖范围和截断状态。
5. 存在未覆盖内容、Tool 错误或未处理截断时，报告不能标记为 complete。
6. 非法行号、伪造证据和没有实际影响的主观意见不能进入最终 Finding。
7. 重要文件类别都有明确的 Query Pack、Reviewer 或确定性校验器。
8. 暂不支持的文件类别会显示检查限制。
9. 混合提交的 Reviewer 输入经过文件级过滤，并有测试验证。
10. 中文文件名、隐藏文件和版本控制特殊路径在提交、合并请求和工作区审查中都能正确处理。
11. 设置更新不会让新任务继续使用旧 Reviewer 客户端，也不会改变已开始任务的配置。
12. 后端测试、语法检查以及涉及的前端和桌面端质量门禁全部通过。

## 16. 审查时长与上下文完整性优化

### 16.1 优化目标

审查性能优化不能通过持续减少 Reviewer 能看到的代码来实现。优化后的审查流程需要同时满足以下目标：

1. 让大模型获得足以理解当前变更的完整语义上下文。
2. 消除相同 Diff、相同文件和相同查询结果的重复审查。
3. 限制 Reflection、Tool 调用和错误重试造成的无界增长。
4. 让审查进度、覆盖范围、缓存命中和预算耗尽状态可以被观测。
5. 通过设计合适的审查逻辑，在审查开始前根据时间和调用预算制定合理的审查策略。
6. 当时间或调用预算耗尽时保留已完成结果，尽可能给出可信的结论。并明确标记未覆盖范围，不能静默丢弃代码。

当前审查时长近似由以下因素共同决定：

~~~text
Diff 批次数 × 上下文批次数 × Reviewer 数量 × Reflection 轮数
    × 每次调用中的 Tool 轮数
~~~

这种调度方式会将 Diff 批次和上下文批次形成笛卡尔积。多个 Reviewer 还可能重复读取同一文件，Reflection 增加上下文后也可能重新执行已经完成的审查。后续优化应消除这些重复路径，同时保留每个审查单元所需的代码关系。

### 16.2 使用语义审查单元

应引入稳定的 `ReviewUnit`，由一个或多个相关 Diff Hunk 组成。审查单元按文件、函数、类、模块或调用关系划分，不能仅按字符数量切分。

每个 `ReviewUnit` 至少包含：

~~~text
unit_id：与 revision 绑定的稳定标识
diff_hunks：属于同一逻辑变更的完整 Diff Hunk
changed_context：变更区域及其必要的前后文
symbol_context：被修改函数、类、方法或接口的定义
related_context：直接调用方、被调用方、配置和相关测试
line_refs：每段上下文的真实文件和行号范围
tool_scope：允许继续查询的文件和行范围
~~~

一个审查单元应尽量让 Reviewer 在单次调用中获得完整的局部语义。单个文件过大时，优先按函数、类和模块边界拆分；只有无法按语义拆分时，才使用字符或行数预算。拆分后的单元应共享模块概览和符号关系，避免模型只看到孤立的代码片段。

对于数万行的大文件，默认提供以下分层上下文：

1. 变更 Hunk 及其前后文；
2. 所属函数、类或模块的必要完整实现；
3. 被修改符号的定义、直接调用方和被调用方；
4. 相关测试和配置；
5. 需要时通过受控 Tool 分页读取更大范围。

这能在控制输入规模的同时保留代码理解所需的因果关系。不能使用“只保留每个文件前若干字符”作为主要策略。

### 16.3 按审查单元调度 Reviewer

Reviewer 调度应由以下形式替代 Diff 与上下文的笛卡尔积：

~~~text
ReviewUnit × Reviewer
~~~

调度器需要具备以下行为：

- 同一 `revision` 下，同一 Reviewer 对同一 `unit_id` 只执行一次主审查；
- 每个审查单元的 Diff 和关联上下文在同一次调用中保持对应关系；
- 不相关的上下文不能因为批次配对进入 Reviewer 输入；
- 审查计划应能表达 Reviewer 与 ReviewUnit 的责任关系；
- 超过单元输入预算时按语义边界继续拆分，不能静默舍弃后续代码。

当前通过 `pair_reviewer_batches` 循环配对 Diff 和上下文批次的实现可以作为防止批次数量乘法增长的临时措施，但它不能作为最终的上下文组织方案。循环配对可能使 Diff 与不相关的上下文组合，后续应迁移到稳定的语义审查单元。

### 16.4 Reflection 只处理新增上下文

Reflection 应基于稳定的审查单元标识判断完成情况，不能根据完整上下文内容生成批次键。建议使用以下去重键：

~~~text
revision + reviewer + unit_id
~~~

流程应调整为：

~~~text
第一次审查：执行全部初始 ReviewUnit
    ↓
Reflection：根据未覆盖文件、Hunk、符号或查询结果生成新增 ReviewUnit
    ↓
只执行新增 ReviewUnit
    ↓
再次 Reflection：继续处理新增范围，不重复已完成单元
~~~

Reflection 需要同时满足以下约束：

- 默认最多执行一轮增量审查；
- 只有存在新的必要上下文或未覆盖 Diff Hunk 时才继续；
- 已完成的 ReviewUnit 不因上下文缓存增加而重新执行；
- 达到 Reflection 预算后保留已有结果，并将报告标记为 `degraded`；
- 空 Finding、FindingGate 过滤结果或低风险结果不能单独说明审查已完成。

### 16.5 建立任务级上下文和 Tool 缓存

多个 Reviewer 读取相同文件时，应共享任务级上下文缓存。缓存键建议包含固定快照和读取范围：

~~~text
revision + file_path + start_line + max_lines
~~~

缓存内容应覆盖：

- 成功读取的文件页；
- 文件行数和文件哈希等稳定元数据；
- 空结果；
- 未授权、文件不存在和其他读取错误。

缓存命中时不应再次访问磁盘或执行相同 Tool。错误结果也需要缓存，避免模型反复请求同一个无效路径。

审查日志和质量指标至少记录：

~~~text
read_file_requests
read_file_cache_hits
read_file_cache_misses
read_file_errors
~~~

变更文件行数统计应采用逐块读取或结果缓存，避免每次构建 `TaskToolContext` 都完整读取同一文件。该项能够降低本地 I/O 和内存分配，但它属于基础优化，不能单独解决 Reviewer 批次爆炸问题。

### 16.6 限制单次 Reviewer 的 Tool 循环

Reviewer 仍然需要通过 Tool 获取超出初始上下文的代码，但必须设置单次审查单元的预算。建议初始参数如下，实际值通过固定快照基准测试校准：

~~~text
Tool 轮数：最多 2 轮
Tool 总调用数：最多 4 次
相同读取参数：直接使用缓存结果
重复的失败请求：直接返回缓存错误
~~~

达到预算后，应将已经取得的 Tool 结果交给模型完成当前审查，并记录：

~~~json
{
  "tool_budget_exhausted": true,
  "tool_calls": 4,
  "tool_rounds": 2
}
~~~

Tool 参数错误，例如模型将 `max_lines` 生成为 `max_line`，应进行兼容归一化并保留错误统计。错误发生后不能让模型无限重试同一请求。

### 16.7 Reviewer 并行化

在审查单元调度、缓存和预算稳定后，可以并行执行相互独立的 Reviewer，以降低墙钟时间：

~~~text
ReviewUnit
    ├── Security Reviewer
    ├── Performance Reviewer
    └── Style Reviewer
~~~

并行化前需要确认：

- 每个 Reviewer 使用独立的调用上下文；
- 数据库 Session 不跨线程共享；
- 日志写入支持并发且顺序可追踪；
- 单个 Reviewer 失败不会中断其他 Reviewer；
- Finding 合并、去重和最终排序保持稳定。

并行化只能降低墙钟时间，不能替代重复调用消除和 Tool 缓存。因此它应在前述调度重构完成后实施。

### 16.8 时间预算、取消和降级报告

审查任务应具备任务级时间和调用预算，并在状态和报告中显示：

~~~json
{
  "planned_units": 8,
  "completed_units": 6,
  "pending_units": 2,
  "primary_llm_calls": 18,
  "tool_calls": 31,
  "cache_hits": 24,
  "elapsed_seconds": 642,
  "budget_exhausted": false
}
~~~

建议先提供以下可配置限制：

- 单任务最大主审查调用数；
- 单任务最大持续时间；
- 单审查单元 Tool 调用数；
- Reflection 增量轮数；
- 单个 ReviewUnit 的输入预算。

当预算耗尽时，任务应停止新增调用，保留已经完成的 Finding，并在报告中列出未处理的 ReviewUnit、文件和 Diff Hunk。前端后续应提供取消任务入口，取消操作需要让 Worker 停止继续提交新的 LLM 和 Tool 请求。

### 16.9 推荐实施阶段

#### 阶段一：修正审查单元和调度

- 从 Diff 批次与上下文批次笛卡尔积迁移到 `ReviewUnit`；
- 按函数、类、模块和调用关系构造语义单元；
- 使用 `revision + reviewer + unit_id` 去重；
- Reflection 只处理新增单元；
- 增加计划、完成、跳过和待处理单元统计。

完成标准：审查次数不再随 Diff 批次数与上下文批次数相乘增长，且每个 Reviewer 收到的 Diff 与关联上下文保持语义对应。

#### 阶段二：建立共享上下文和 Tool 缓存

- 建立任务级文件页缓存；
- 缓存成功结果、空结果和错误结果；
- 复用不同 Reviewer 之间的上下文；
- 记录缓存命中率和真实磁盘读取次数；
- 对变更文件行数统计增加逐块读取或按 revision 缓存。

完成标准：同一 revision、文件和行范围不会重复执行相同的实际读取。

#### 阶段三：限制 Tool 循环并修复错误重试

- 增加 Tool 轮数和总调用数限制；
- 兼容模型生成的参数别名；
- 去重重复 Tool 请求和重复错误；
- 在预算耗尽时生成带限制说明的结果。

完成标准：单个 ReviewUnit 的 Tool 调用数量有明确上限，Tool 失败不会导致无界重试。

#### 阶段四：并行 Reviewer 和任务取消

- 并行执行独立 Reviewer；
- 增加任务级时间预算；
- 增加取消接口和 Worker 停止检查；
- 验证并发日志、数据库和 Finding 合并的一致性；
- 验证开发后端和打包 sidecar 使用同一份新代码。

完成标准：在不减少 ReviewUnit 语义上下文的情况下缩短墙钟时间，任务可以主动停止并保留可解释的部分结果。

### 16.10 性能与质量验收指标

使用固定 `revision`、固定模型配置和固定审查计划进行基准测试，至少比较以下指标：

| 指标 | 验收要求 |
| --- | --- |
| 主审查调用数 | 不出现 Diff 批次与上下文批次的乘法增长 |
| ReviewUnit 覆盖 | 每个计划单元有完成、失败或明确未处理状态 |
| 上下文完整性 | 每个单元包含完整相关 Diff、符号定义和必要关联代码 |
| Reflection 重复率 | 已完成单元不因新增上下文重新执行 |
| Tool 重复率 | 相同读取键只产生一次真实读取 |
| Tool 失败重试 | 重复错误请求不会无限增长 |
| 截断可见性 | 所有输入截断都有范围记录和报告状态 |
| 结果一致性 | 相同 revision 和模型配置的 Finding 差异处于可接受波动范围 |
| 墙钟时间 | 在保持上下文完整性的前提下相对当前基线明显下降 |

当前出现的数十至上百个 Reviewer 批次、未完成文件持续增加、审查输入截断和 Tool 调用失败，应分别通过上述指标定位。不能仅以最终 Finding 数量减少判断审查变快或质量提高。
