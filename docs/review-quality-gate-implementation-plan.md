# 审查质量门槛与低价值意见治理实施方案

## 1. 背景

当前审查工具会将 Reviewer 的输出直接转换为 Finding，并展示在最终 Review Report 中。对于 `b26c660` 这类只更新发布元数据的提交，工具生成了以下低价值意见：

- 将 JSON 字段顺序差异视为问题；
- 将转义换行和字符串长度视为维护问题；
- 在没有读取实际安装包的情况下，认为 SHA256 可能不匹配。

这些意见的共同问题不是文件类型特殊，而是没有经过“是否影响行为”“是否有证据”“是否值得采取行动”三个层面的判断。

本方案的目标是建立通用的审查质量机制，使审查工具在面对新的文件类型、新的 Reviewer 和新的检查规则时，仍然能够抑制“为了审查而审查”的意见。

## 2. 目标与非目标

### 2.1 目标

1. 只将具有实际影响、直接证据和可执行建议的问题输出为 Finding。
2. 将不同类型的变更交给适合的审查方式，而不是统一交给通用 LLM Reviewer。
3. 将“已验证的问题”“检查结果”和“无法验证的外部事实”分开表达。
4. 不要求用户逐条确认 Finding，通过低成本抽样发现系统性误报。
5. 对发布清单、锁文件、工作流和其他未来出现的特殊文件使用通用判断原则，而不是维护不断增长的排除名单。

### 2.2 非目标

- 不追求输出尽可能多的 Finding。
- 不把用户是否修改代码作为问题正确性的唯一依据。
- 不以用户未点击反馈按钮推断意见无效。
- 不通过提交作者、提交消息或文件名单独决定是否跳过审查。
- 不在本阶段实现完整的远程资产下载和所有外部服务校验。

## 3. 核心原则

### 3.1 审查对象不等于所有变更

应先判断变更可能影响的对象：

| 影响对象 | 适合的审查方式 |
| --- | --- |
| 程序运行行为 | 代码 Reviewer、测试和静态分析 |
| 数据格式或接口契约 | Schema、兼容性和解析校验 |
| 权限与安全边界 | Security Reviewer、权限规则校验 |
| 构建、部署和发布流程 | Workflow Reviewer、配置校验 |
| 依赖解析结果 | 包管理器和依赖安全校验 |
| 纯表示层变化 | 默认不生成通用 Finding |

例如，`update/windows.json` 仍然可能影响自动更新，因此不能简单跳过，而应使用发布清单校验器。`.github/workflows/*.yml` 即使由自动化账号修改，也应继续检查权限和命令注入风险。

### 3.2 Reviewer 输出只是候选意见

Reviewer 返回的内容首先进入候选 Finding 集合，经过统一质量门槛后，才进入最终 Report。

```text
变更文件
    ↓
审查范围分类
    ↓
选择 Reviewer 或确定性校验器
    ↓
生成候选意见
    ↓
Finding 质量门槛
    ↓
最终 Review Report
```

### 3.3 默认保守输出

当工具无法确认外部事实或无法证明实际影响时，应选择不生成 Finding。审查工具的默认行为应是“证据不足则暂不报告”，而不是将不确定性包装成 LOW 问题。

## 4. 统一审查范围分类

新增 `ChangeScopeClassifier` 模块，负责根据变更文件、diff 内容和可选的提交元数据，生成文件级审查范围。

建议的内部分类如下：

```text
source_code
configuration
release_manifest
dependency_lock
ci_workflow
documentation
generated_artifact
unknown
```

分类器输出不直接决定“是否审查”，而是决定“使用哪种审查适配器”。

### 4.1 分类依据

分类优先级如下：

1. 项目声明的文件语义和 Schema；
2. 文件路径与扩展名；
3. 文件是否由生成流程维护；
4. diff 是否包含语义字段变化；
5. 提交消息和作者作为辅助信息。

提交作者和提交消息不能单独作为跳过条件，因为攻击者或错误流程可能产生相同的元数据。

### 4.2 混合提交处理

分类必须以文件为粒度。一个提交同时修改源码和发布清单时：

- 源码文件继续进入代码 Reviewer；
- 发布清单进入确定性校验器；
- 发布清单不进入通用 Style Reviewer；
- 提交整体仍保留安全和发布风险检查。

## 5. 确定性校验器

对于能够通过解析器、Schema 或外部工具直接判断的内容，优先使用确定性校验器，不调用 LLM 生成主观意见。

### 5.1 发布清单校验器

新增 `ReleaseManifestValidator`，首先支持 `update/windows.json`，接口不应绑定单个文件名：

```python
validate_release_manifest(
    path: str,
    changed_lines: set[int],
    repo_root: str,
) -> ValidationResult
```

检查内容：

- JSON 是否可解析；
- 必填字段是否存在；
- `version` 是否符合项目版本格式；
- `download_url` 和 `release_url` 是否与版本一致；
- `sha256` 是否为 64 位十六进制字符串；
- `release_date` 是否为合法 ISO 时间；
- 远程资产可用时，SHA256 是否与实际资产一致。

### 5.2 检查结果与 Finding

确定性校验器返回三类结果：

```text
pass          校验通过
finding       已确定存在错误
unverified    当前环境无法验证
```

例如：

```text
sha256 格式正确，但没有访问 Release 资产的权限
→ unverified，不生成 Finding

sha256 已与下载的安装包计算结果不一致
→ finding，定位到 sha256 字段并说明实际校验结果
```

## 6. Finding 质量门槛

新增统一的 `FindingGate`，位于 Reviewer 输出解析之后、报告聚合之前。

### 6.1 必要条件

每条 Finding 必须满足：

1. 文件位于本次变更范围，或能明确说明受影响的关联文件；
2. 能指向具体 diff、代码行、Schema 规则或工具结果；
3. 能描述现实的失败场景、风险或行为变化；
4. 建议具有明确的处理动作；
5. 建议成本与问题影响相匹配；
6. 不是单纯的个人偏好、格式偏好或未验证猜测。

### 6.2 默认过滤项

以下内容默认不进入最终 Finding：

- “无法确认，建议检查”；
- 没有行为后果的字段顺序差异；
- 单纯的字符串长度、转义换行或格式差异；
- 没有项目约束支持的命名和排版偏好；
- 只说明理想状态，没有实际失败场景；
- 无法通过当前快照或工具结果证明的外部事实。

### 6.3 内部证据字段

为保持前端现有 Finding 结构兼容，证据字段可以先作为内部字段保存，后续再决定是否展示：

```json
{
  "evidence_type": "diff | static_check | tool_verified | external_unverified",
  "evidence": "具体证据摘要",
  "impact": "behavior | security | compatibility | build | maintainability",
  "confidence": 0.92
}
```

其中 `external_unverified` 不允许通过 FindingGate。

## 7. Reviewer 提示词调整

提示词是辅助约束，不能替代 FindingGate。

Style Reviewer 应从“达到阈值就报告”改为“存在可证明风险才报告”。专业术语统一使用：

- 代码风格问题；
- 可维护性风险；
- 结构性风险；
- 运行风险；
- 安全风险。

建议加入以下规则：

```text
只报告与当前变更直接相关且有证据的问题。
代码长度、参数数量、行长度和命名差异本身不是问题。
只有当这些因素造成实际错误、风险或维护障碍时才报告。
对于机器生成文件和发布元数据，优先依赖确定性校验器。
无法验证外部事实时返回空数组，不要生成“无法确认”类 Finding。
如果没有满足条件的问题，必须返回 []。
```

其他 Reviewer 也应遵循相同的证据和影响要求。

## 8. “未知”与“问题”分离

最终报告模型增加可选的检查摘要，例如：

```json
{
  "checks": [
    {
      "name": "release_artifact_sha256",
      "status": "unverified",
      "message": "当前环境未获取 Release 安装包"
    }
  ]
}
```

`checks` 不计入：

- `total_findings`；
- `by_severity`；
- `risk_level`。

这样可以保留审查边界和验证限制，又不会把限制本身展示成缺陷。

## 9. 质量评估方式

不把用户逐条采纳作为主要指标。用户没有点击、不修改代码或关闭报告，都只能视为未知，不能推断为无效。

### 9.1 自动质量指标

持续记录以下代理指标：

- 变更范围命中率：Finding 是否指向本次变更文件和行；
- 证据覆盖率：Finding 是否包含静态检查或工具证据；
- 无定位意见比例：`line=0` 或无法定位到具体证据的比例；
- 重复意见率：同一审查中重复报告同类问题的比例；
- 空报告稳定性：纯元数据提交是否稳定返回零 Finding；
- Reviewer 波动率：相同提交重复审查时结果是否大幅变化；
- FindingGate 拦截率：某类 Reviewer 输出是否经常被质量门槛过滤。

这些指标用于发现系统性噪声，不冒充真实准确率。

### 9.2 抽样人工评估

定期从审查结果中抽取少量 Finding，由维护者集中复核，而不是要求用户逐条点击。

建议规则：

- 每 20 次审查抽取约 5 条 Finding；
- 高危和中危优先抽取；
- 每个 Reviewer 和问题类别都应有最低样本量；
- 复核结果为“有效”“无效”“无法判断”。

抽样有效率为：

```text
有效数量 /（有效数量 + 无效数量）
```

“无法判断”和没有参与复核的样本不计入分母。

当某类意见达到 20～30 条明确复核样本后：

- 有效率低于 60%：降级为 Check 或关闭默认输出；
- 有效率处于 60%～80%：保留，但提高证据要求；
- 有效率高于 80%：保留当前策略，继续抽样监控。

这些阈值用于运营校准，不作为问题正确性的数学保证。

## 10. 数据记录

为支持抽样和规则迭代，Finding 需要稳定标识。建议生成：

```text
finding_key = hash(review_id + file + line + title + category)
```

新增可选的反馈记录，不要求用户主动填写：

```text
finding_feedback
  id
  finding_key
  verdict: useful | invalid | uncertain
  reason
  reviewer
  created_at
```

只有维护者或用户主动标记时写入记录。未标记的 Finding 不参与有效率统计。

## 11. 代码改动位置

建议按以下模块划分实现：

| 模块 | 职责 |
| --- | --- |
| `backend/app/engine/scope.py` | 变更范围分类和文件级审查计划 |
| `backend/app/engine/validators/` | 发布清单、依赖、工作流等确定性校验器 |
| `backend/app/engine/finding_gate.py` | Finding 证据、影响和行动性过滤 |
| `backend/app/engine/workflow.py` | 在 Planning 和 Report 聚合之间接入分类器与门槛 |
| `backend/app/engine/reviewers/*.py` | 调整提示词，减少基于阈值的主观意见 |
| `backend/app/models/schemas.py` | 增加可选的 checks 和内部证据模型 |
| `backend/app/models/repo.py` | 持久化检查摘要和可选反馈 |
| `backend/tests/` | 范围分类、校验器、FindingGate 和回归场景 |

不建议把分类、过滤和校验逻辑继续堆积在 `workflow.py` 中。Workflow 只负责编排，各模块通过小接口提供深层实现，便于单独测试和替换。

## 12. 分阶段实施

### 阶段一：建立 FindingGate

- 增加候选 Finding 到最终 Finding 的过滤步骤；
- 强制要求变更范围、证据、影响和可执行建议；
- 过滤“无法确认”“建议检查”和纯格式偏好；
- 增加 `b26c660` 回归测试。

完成标准：当前提交不再生成三条 LOW 意见。

### 阶段二：建立 ChangeScopeClassifier

- 实现文件级范围分类；
- 修改 Planning，避免未知文件默认进入 Style Reviewer；
- 支持混合提交的差异化审查；
- 保留工作流和安全文件的审查能力。

完成标准：新增文件类型不会因为未加入排除名单而自动触发通用风格审查。

### 阶段三：实现确定性校验器

- 实现发布清单校验；
- 将校验通过、校验失败和无法验证分离；
- 后续按需求增加依赖锁文件和 CI 工作流校验器。

完成标准：可验证的格式和契约问题由工具直接确认，外部事实不再由 LLM 猜测。

### 阶段四：质量抽样和校准

- 增加 Finding 稳定标识；
- 增加维护者抽样复核入口；
- 统计证据覆盖率、无定位意见比例、重复率和抽样有效率；
- 根据类别有效率调整 Reviewer 和 FindingGate 规则。

完成标准：能够识别并持续降低某类 Reviewer 的系统性误报。

## 13. 验收场景

至少覆盖以下测试：

1. `b26c660`：返回 0 条 Finding，发布字段校验全部通过；
2. JSON 字段顺序变化：不生成 Finding；
3. `release_notes` 较长或包含转义换行：不生成 Finding；
4. SHA256 格式正确但远程资产不可访问：生成 `unverified` Check；
5. SHA256 与实际安装包不一致：生成有工具证据的 Finding；
6. 源码与发布清单同时变更：源码继续由相关 Reviewer 审查；
7. 新增未知文件类型：不自动触发通用 Style Reviewer；
8. Reviewer 输出“建议检查但无法证明”：被 FindingGate 拦截；
9. Finding 无法定位到变更范围：被 FindingGate 拦截；
10. 同一提交重复审查：结果在允许的 LLM 波动范围内保持稳定。

## 14. 最终质量目标

审查工具的核心指标不是 Finding 数量，而是：

```text
每条 Finding 都有证据；
每条 Finding 都说明实际影响；
每条 Finding 都能指导行动；
不确定信息不会伪装成问题；
系统性误报能够通过抽样被发现和修正。
```

这套机制可以处理发布清单以外的未来文件类型，避免审查系统通过不断增加例外规则来维持表面上的准确性。
