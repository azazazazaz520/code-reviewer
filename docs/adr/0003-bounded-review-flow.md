# ADR 0003：采用有界的四阶段审查流程

状态：已采用（2026-09-07）

## 背景

旧流程把规划、上下文收集、自由 Tool 循环、反思和 JSON 收口拆成多个可回退阶段。
在变更较大或模型输出异常时，阶段会互相放大调用次数，造成输入截断、Tool 预算耗尽、
缓存前缀不稳定和审查结果不完整。

## 决策

工作流固定为四个节点：

1. `Load PR` 固定审查快照和当前 Diff。
2. `Prepare Review` 一次完成审查计划、确定性校验、变更文件上下文读取和 Reviewer 批次构造。
3. `Run Reviews` 对每个批次执行一次结构化审查。模型可以一次性返回 `context_requests`，
   系统按授权范围读取后最多执行一次补充审查；补充响应必须返回空请求数组。
4. `Generate Report` 执行 FindingGate 并生成最终报告。

JSON 格式修复仅在实际 JSON 解析失败时执行一次；Provider 的 `finish_reason=length`
只作为诊断信号，不能替代对返回内容的解析。修复请求使用独立预算并显式关闭思考模式。
主审查、补充审查和 JSON 修复分别使用独立 Token 配置，并全部显式关闭思考模式，避免隐藏推理
消耗结构化输出预算。默认关闭 CRG 深度上下文；需要时
由设置显式启用。完整 Hunk 不拆分，多个 ReviewUnit 只在 Reviewer 批次边界合并。
Reviewer 输出协议统一为对象形式；每个批次最多保留 5 条最重要的 Finding，并限制标题、原因、建议和证据的长度，避免单条结论重复扩写耗尽 JSON 输出预算。JSON 修复只保留原始响应中已经完整的 Finding，不补写新的结论。

## 后果

- 默认调用路径没有自由 Tool 循环和 Reflection Loop，执行次数可由批次数量直接估算。
- Diff 始终作为完整证据发送；文件上下文只读取变更范围附近的固定窗口，超出预算记录为诊断事件。
- 关联上下文必须来自 Prepare 阶段批准的引用，模型不能通过参数访问任务范围之外的文件。
- 跨 Reviewer 的重复 Finding 在收口阶段去重并单独计数，不计入可操作的过滤告警；只有证据、范围或结构校验拒绝的 Finding 才计入 `filtered_findings`。
- 旧设置字段在加载时只做一次迁移，不再参与运行时决策。
